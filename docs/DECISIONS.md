# บันทึกการตัดสินใจ — Garden Guardian

ไฟล์นี้มี 2 ส่วน

1. **โจทย์ที่ยังเปิดอยู่** — เรื่องที่รู้ว่าต้องแก้ แต่ยังไม่ตัดสินใจ พร้อมเหตุผลว่าทำไมถึงยังไม่ตัดสิน
2. **บันทึกการตัดสินใจ** — เรื่องที่ตัดสินไปแล้วและเปลี่ยนทิศทางโปรเจกต์ พร้อมเหตุผล เรียงจากใหม่ไปเก่า

การแยกสองส่วนนี้ตั้งใจ เพราะการรู้ว่า "ยังไม่รู้อะไร" มีค่าพอ ๆ กับการรู้ว่าตัดสินใจอะไรไปแล้ว

## ขอบเขตของงานรอบนี้

โฟกัสปัจจุบันอยู่ที่ **Phase 1 และ Phase 2 เท่านั้น**

- **Phase 1** — สมองส่วนแยกแยะพืช และตรรกะตัดสินใจ `protect` / `removal_candidate` / `review`
- **Phase 2** — ground-plane homography แปลงพิกเซลเป็นเซนติเมตรบนพื้น

Phase 3–5 (coverage map, edge deployment, ฐานเคลื่อนที่จริง) อยู่ใน roadmap แต่ยังไม่ลงมือ

# ส่วนที่ 1 — โจทย์ที่ยังเปิดอยู่

## Open problem: localization — หุ่นจะรู้ได้อย่างไรว่าตัวเองอยู่ตรงไหน

*ตั้งโจทย์เมื่อ 2026-08-05*

> **สถานะ: ยังไม่เลือกวิธี และตั้งใจว่ายังไม่ถึงเวลาเลือก**
>
> หัวข้อนี้เป็นการตั้งคำถามให้ชัด ไม่ใช่การเสนอคำตอบ ไม่มีตัวเลือกไหนถูกทำเครื่องหมายว่า
> "ดีที่สุด" เพราะข้อมูลที่จำเป็นต่อการตัดสินยังไม่มีอยู่ในมือ

### โจทย์คืออะไร

Phase 2 ทำให้หุ่นตอบได้ว่า *"วัชพืชต้นนี้อยู่หน้าฉัน 32 ซม. เยื้องซ้าย 11 ซม."*
ซึ่งเป็นพิกัดเทียบกับตัวหุ่นในเฟรมนั้น พอหุ่นขยับ คำตอบนั้นก็หมดอายุทันที

โจทย์ที่ยังไม่มีคำตอบคือ ทำอย่างไรให้หุ่นตอบได้ว่า *"วัชพืชต้นนี้อยู่ตรงไหนของสวน"*
ซึ่งต้องรู้ก่อนว่า **ตัวหุ่นเองอยู่ตรงไหนของสวน** — นั่นคือปัญหา localization

ถ้าไม่มีคำตอบนี้ จะทำสิ่งเหล่านี้ไม่ได้เลย: กลับไปหาวัชพืชต้นเดิมซ้ำ, จำว่าไถตรงไหนไปแล้ว
(coverage map), บอกว่าตรงไหนยังไม่เคยผ่าน, หรือเทียบผลข้ามวันว่าวัชพืชโตขึ้นไหม

### ทำไมหุ่นเคลื่อนที่บนสนามหญ้าถึงประมาณตำแหน่งตัวเองยาก

จุดตั้งต้นที่ทุกคนนึกถึงก่อนคือ **wheel odometry** — นับรอบล้อแล้วคำนวณย้อนว่าเคลื่อนไปเท่าไร
วิธีนี้ใช้ได้ดีบนพื้นแข็งเรียบ แต่บนสนามหญ้ามีปัญหาซ้อนกันหลายชั้น

1. **ล้อลื่น (wheel slip)** — หญ้าเปียก น้ำค้างตอนเช้า หรือหลังฝน ทำให้ล้อหมุนฟรี
   ตัวนับบอกว่าเคลื่อนไป 50 ซม. แต่จริง ๆ ไปแค่ 35 ซม. และหุ่นไม่มีทางรู้ว่าพลาด
2. **ระยะต่อรอบล้อไม่คงที่** — ล้อจมลงไปในหญ้าลึกไม่เท่ากันตามความสูงและความหนาแน่นของหญ้า
   ทำให้รัศมีล้อที่ใช้งานจริงเปลี่ยนไปเรื่อย ๆ สูตรคำนวณที่ตั้งค่าไว้ตายตัวจึงเพี้ยน
3. **พื้นไม่เรียบ** — เนิน หลุม รากไม้ ทำให้หุ่นเอียงและเบี่ยงทิศโดยที่ล้อยังหมุนปกติ
4. **ความคลาดเคลื่อนสะสม (drift)** — odometry คือการบวกระยะทีละก้าว ความผิดพลาดเล็ก ๆ
   ในแต่ละก้าวจะสะสมไปเรื่อย ๆ ไม่มีวันหายเอง ยิ่งวิ่งนานยิ่งเพี้ยนมาก
   **และไม่มีอะไรมาดึงให้กลับมาตรง**
5. **ไม่มีจุดอ้างอิงที่ตรึงกับสวน** — ต่างจากหุ่นแบบ gantry ที่มี home switch ให้วิ่งไปชน
   แล้วรีเซ็ตเป็น `(0,0)` ได้ทุกเมื่อ หุ่นตัวนี้ไม่มีอะไรแบบนั้นเลย

ข้อ 4 กับ 5 รวมกันคือหัวใจของปัญหา: **มี error ที่สะสมไม่หยุด และไม่มีอะไรมารีเซ็ต**
ตัวเลือกทุกตัวข้างล่างนี้คือความพยายามตอบข้อนี้ด้วยวิธีต่างกัน

### ตัวเลือกที่มีอยู่

รายการนี้เรียงตามลำดับที่พูดถึงกันบ่อย **ไม่ใช่การจัดอันดับ**

#### Visual odometry (VO) — ประมาณการเคลื่อนที่จากภาพที่กล้องเห็น

| | |
|---|---|
| **ข้อดี** | ใช้กล้องตัวเดียวกับที่ใช้ตรวจพืชอยู่แล้ว ไม่ต้องซื้อเซ็นเซอร์เพิ่ม · ไม่ต้องดัดแปลงสวนเลย ไม่ต้องปักอะไร · ไม่ยึดติดกับล้อ จึงไม่โดนปัญหาล้อลื่นโดยตรง |
| **ข้อเสีย** | สนามหญ้ามีลวดลายซ้ำกันทั้งผืน หา feature ที่จับยึดได้ยาก · หญ้าขยับตามลม ทำให้จุดอ้างอิงในภาพไม่นิ่ง ผิดสมมติฐานพื้นฐานของ VO ที่ว่าฉากอยู่กับที่ · แสงและเงาเปลี่ยนทั้งวัน · กินกำลังประมวลผลมากบนบอร์ดเล็ก · **ยัง drift สะสมอยู่ดี** แค่ช้ากว่า wheel odometry ไม่ได้แก้ปัญหาข้อ 4 |

#### ArUco marker — ปักป้ายลายขาวดำไว้ในสวนเป็นจุดอ้างอิง

| | |
|---|---|
| **ข้อดี** | ต้นทุนต่ำมาก พิมพ์ลงกระดาษหรือแผ่นพลาสติกได้ · OpenCV รองรับในตัว ไม่ต้องลงไลบรารีเพิ่ม · ให้ตำแหน่งแบบสัมบูรณ์ทุกครั้งที่มองเห็น จึง **รีเซ็ต drift ได้** ซึ่งตอบข้อ 4 ตรง ๆ · debug ง่าย เห็นด้วยตาว่าทำงานหรือไม่ · ใช้ homography ที่ทำใน Phase 2 ต่อยอดได้ |
| **ข้อเสีย** | ต้องปักป้ายไว้ในสวนจริง ซึ่งดูไม่สวยและเจ้าของบ้านอาจไม่ยอม · ป้ายโดนฝน แดดจนสีซีด ลมพัดล้ม หรือหญ้าขึ้นบัง · ใช้ได้เฉพาะจังหวะที่กล้องเห็นป้าย ระหว่างที่ไม่เห็นต้องพึ่งวิธีอื่นอยู่ดี · หุ่นเตี้ยติดพื้น มุมกล้องต่ำ อาจเห็นป้ายได้ยากกว่าที่คิด · ต้องวัดตำแหน่งป้ายให้แม่นตอนติดตั้ง ถ้าวัดผิดก็ผิดทั้งระบบ |

#### IMU — เซ็นเซอร์วัดความเร่งและการหมุน

| | |
|---|---|
| **ข้อดี** | ถูก เล็ก กินไฟน้อย · วัดการหมุนและความเอียงได้แม่นในช่วงสั้น ๆ · ตรวจจับเหตุการณ์ผิดปกติได้ เช่น หุ่นเอียง ชน หรือล้อลื่น · ทำงานได้ในที่มืดและไม่สนใจสภาพแสง |
| **ข้อเสีย** | **ไม่ใช่ระบบ localization ในตัวเอง** — ให้ตำแหน่งไม่ได้โดยตรง ต้อง integrate ความเร่งสองชั้นซึ่ง drift เร็วมากในระดับวินาทีถึงนาที · เข็มทิศในตัวโดนสนามแม่เหล็กจากมอเตอร์รบกวน · โดยโครงสร้างแล้วเป็นตัวเสริมให้วิธีอื่น ไม่ใช่ตัวหลัก (ข้อนี้เป็นคุณสมบัติของเซ็นเซอร์ ไม่ใช่คำแนะนำ) |

#### RTK-GPS — GPS ความละเอียดสูงที่ใช้สถานีฐานช่วยแก้ค่า

| | |
|---|---|
| **ข้อดี** | ให้พิกัดสัมบูรณ์ระดับเซนติเมตร ไม่มี drift สะสม · ผูกกับพิกัดโลกจริง (lat/lon) จึงต่อกับ GIS และงาน GeoAI ได้โดยตรง · ไม่ต้องปักอะไรในสวน ไม่ต้องพึ่งลักษณะของฉาก |
| **ข้อเสีย** | ราคาสูงที่สุดในลิสต์ ต้องมีทั้งตัวรับบนหุ่นและสถานีฐาน หรือจ่ายค่าบริการรายเดือน · ต้องเห็นท้องฟ้าโล่ง แต่สวนหลังบ้านมักมีต้นไม้ ชายคา รั้ว หรือกำแพงบัง ทำให้สัญญาณตกและเกิด multipath · สวนหลังบ้านขนาดเล็กอาจมี "เงา" ของสัญญาณเป็นบริเวณกว้าง · กินไฟมากกว่าตัวเลือกอื่น · ต้องประเมินว่าความแม่นที่ได้จริงในสวนนั้น ๆ พอกับขนาดเขตกันชนรอบพืชหรือไม่ |

#### SLAM — สร้างแผนที่และหาตำแหน่งตัวเองไปพร้อมกัน

| | |
|---|---|
| **ข้อดี** | ตอบทั้งเรื่องตำแหน่งและ coverage map ในคราวเดียว · loop closure ช่วยดึง drift กลับเมื่อกลับมาที่เดิม ซึ่งตอบข้อ 4 · ไม่ต้องดัดแปลงสวน · มี ecosystem และงานวิจัยรองรับเยอะ นำไปอ้างอิงในเชิงวิชาการได้ |
| **ข้อเสีย** | ซับซ้อนที่สุดและกินทรัพยากรมากที่สุดในลิสต์ · สนามหญ้ากลางแจ้งเป็นเคสที่ยากสำหรับ SLAM เพราะฉากซ้ำ ไม่มีผนังหรือมุมห้องให้จับ และแสงเปลี่ยนตลอดวัน · พืชโตและเปลี่ยนรูปร่างตามเวลา แผนที่ที่สร้างไว้เมื่อสัปดาห์ก่อนอาจใช้ไม่ได้ · ถ้าใช้ LiDAR ราคาสูง และ LiDAR 2D ที่กวาดในแนวนอนแทบไม่เห็นอะไรที่เป็นประโยชน์ในสนามหญ้า · งานติดตั้งและจูนพารามิเตอร์เยอะ |

**หมายเหตุสำคัญ:** ห้าข้อนี้ไม่ได้แยกขาดจากกันและไม่ใช่โจทย์ที่ต้องเลือกมาหนึ่งข้อ
ในงานจริงมักใช้หลายอย่างร่วมกันเพื่อชดเชยจุดอ่อนของกันและกัน การจะผสมอย่างไร
ก็เป็นส่วนหนึ่งของโจทย์ที่ยังไม่ได้ตอบเช่นกัน

### ทำไมถึงยังไม่เลือกตอนนี้

**เพราะยังไม่มีข้อมูลพอที่จะเรียกว่าการเลือก ถ้าเลือกตอนนี้คือการเดา**

- **ยังไม่มีกล้องจริง** — ไม่รู้มุมมอง ความละเอียด เฟรมเรต และคุณภาพในที่แสงน้อย
  จึงประเมิน visual odometry และ ArUco ไม่ได้เลย
- **ยังไม่มีตัวหุ่น** — ไม่รู้ความสูงที่จะติดกล้อง ชนิดล้อ ความเร็ว กำลังประมวลผลบนบอร์ด
  และงบไฟจากแบตเตอรี่
- **ไม่รู้ขนาดและรูปร่างของสวนจริง** — สวน 5×5 เมตร กับ 30×30 เมตร เป็นคนละโจทย์กัน
  ทั้งเรื่องความแม่นที่ต้องการและ drift ที่ยอมรับได้
- **ไม่รู้ว่ามีอะไรบังท้องฟ้าบ้าง** — จึงประเมิน RTK-GPS ไม่ได้

ต้นทุนของการเดาผิดในเรื่องนี้สูง เพราะแต่ละทางเลือกผูกกับการซื้อฮาร์ดแวร์และ
โครงสร้างซอฟต์แวร์ที่ต่างกันมาก การรื้อทีหลังแพงกว่าการรอ

### ต้องรู้อะไรก่อนถึงจะเลือกได้

รายการนี้คือเงื่อนไขปลดล็อกของหัวข้อนี้ ตอบครบเมื่อไรถึงค่อยกลับมาตัดสิน

1. **ขนาดและรูปร่างของสวนจริง** เป็นเมตร พร้อมผังคร่าว ๆ ว่าอะไรบังท้องฟ้าตรงไหน
2. **ความแม่นที่ "พอ" คือเท่าไร** — ข้อนี้สำคัญที่สุดและมักถูกข้าม ความแม่นที่ต้องการ
   ผูกกับขนาดเขตกันชนรอบพืชปลูก ถ้ากันชนกว้าง 20 ซม. การไล่ล่าความแม่นระดับ 2 ซม.
   ก็ไม่มีความหมาย ตัวเลขนี้เปลี่ยนคำตอบของทั้งหัวข้อ
3. **สเปกกล้องจริงที่จะติด** และความสูงที่ติดได้
4. **บอร์ดประมวลผลและงบไฟ** — Raspberry Pi กับ Jetson รับภาระได้ไม่เท่ากัน
5. **งบประมาณฮาร์ดแวร์ทั้งก้อน** และสัดส่วนที่ยอมจ่ายให้เรื่อง localization โดยเฉพาะ
6. **ยอมดัดแปลงสวนได้แค่ไหน** — ปักป้าย ArUco ได้หรือไม่ ปักได้กี่จุด ตรงไหนบ้าง
7. **หุ่นต้องทำงานตอนไหน** — เฉพาะกลางวันแดดดี หรือต้องทำงานตอนเช้าที่มีน้ำค้าง
   และหลังฝนด้วย
8. **ต้องกลับมาที่เดิมซ้ำข้ามวันไหม** — ถ้าต้องการแค่ครอบคลุมพื้นที่ให้ทั่วภายในรอบเดียว
   โจทย์จะง่ายกว่าการต้องจำตำแหน่งวัชพืชข้ามวันมาก ข้อนี้เปลี่ยนขอบเขตของปัญหาทั้งหมด

### ทำไมการปล่อยให้เป็นโจทย์เปิดถึงเป็นการตัดสินใจที่ตั้งใจ

Phase 2 คือสะพานจากงาน computer vision ไปสู่งานเชิงพื้นที่ (GeoAI) ตัว homography
ทำให้ผลลัพธ์จากภาพกลายเป็นระยะจริงบนพื้น และขั้นถัดไปคือการอ้างอิงระยะเหล่านั้น
เข้ากับระบบพิกัดของสวน ซึ่งก็คือ localization

การเขียนโจทย์นี้ให้ชัดโดยยังไม่ฟันธง แสดงว่าเข้าใจ trade-off ของแต่ละทาง และรู้ว่า
ต้องมีข้อมูลอะไรก่อนถึงจะตัดสินได้ ซึ่งตรงกับวิธีทำงานวิจัยมากกว่าการเลือกไปก่อน
แล้วค่อยหาเหตุผลมาสนับสนุนย้อนหลัง

# ส่วนที่ 2 — บันทึกการตัดสินใจ

## 2026-08-04 — เปลี่ยนจาก gantry เป็นหุ่นเคลื่อนที่บนพื้น

**เดิม:** หุ่นแบบ gantry คือโครงราง X-Y ครอบแปลงปลูกไว้ ตัวหัวกำจัดเลื่อนไปมาบนราง
แบบเครื่อง CNC มี Home switches ที่มุมรางเป็นจุด `(0,0)` ตายตัว

**ใหม่:** หุ่นเตี้ยทรงกลมที่ไถลไปบนพื้นเอง วิ่งอิสระบนสนามหญ้าแบบเครื่องดูดฝุ่น
ไม่มีโครง ไม่มีราง ไม่มีจุดอ้างอิงที่ตรึงกับสวน

### เหตุผล

1. **ตรงกับไอเดียตั้งต้น** ภาพที่อยากได้ตั้งแต่แรกคือ "หุ่นดูดฝุ่นที่กินหญ้า"
   ไม่ใช่เครื่องจักรที่ครอบแปลงไว้ การทำ gantry คือเปลี่ยนโจทย์ให้ง่ายลงจนไม่ใช่
   ของที่อยากได้จริง

2. **ปัญหาที่น่าสนใจอยู่ที่ localization กับ coverage** พอหุ่นเคลื่อนที่ได้ คำถามจะกลายเป็น
   "ตอนนี้ฉันอยู่ตรงไหน" และ "ไถตรงไหนไปแล้วบ้าง" ซึ่งเป็นคำถามเชิงพื้นที่แท้ ๆ

3. **เชื่อมกับทิศทาง GeoAI ที่จะใช้ใน portfolio ป.โท** เรื่อง coverage map,
   การอ้างอิงพิกัด, และการประมาณตำแหน่งบนพื้นที่จริง เป็นแกนเดียวกับงาน GeoAI
   ทำเรื่องนี้แล้วต่อยอดเข้าพอร์ตได้โดยตรง

4. **gantry ตัดปัญหานั้นทิ้งทั้งหมด** ถ้ามีรางกับ Home switch ตำแหน่งจะรู้ได้จาก
   การนับสเต็ปมอเตอร์ ไม่ต้องประมาณอะไรเลย ซึ่งแปลว่าไม่เหลือส่วนที่เป็น GeoAI
   ให้ทำ และไม่เหลือปัญหาที่คุ้มจะใส่ในพอร์ต

### ผลกระทบ

- roadmap ขยับ: ground-plane calibration และ coverage map ขึ้นมาเป็น Phase 2 และ 3
  ส่วนการต่อกับฐานเคลื่อนที่จริงถูกเลื่อนไปเป็น Phase 5
- เอกสารทั้งหมดตัดเรื่อง Home switches, machine origin `(0,0)`, limit switch
  และราง X-Y ออก
- เพิ่ม `src/ground_plane.py` เป็นโครงของ Phase 2
- **ยอมรับปัญหาใหม่ที่ยังไม่มีคำตอบ: localization** รายละเอียดอยู่ในส่วนที่ 1
  ของไฟล์นี้ และใน [CHAT_HANDOFF_TH.md](CHAT_HANDOFF_TH.md)

### สิ่งที่ไม่เปลี่ยน

กฎความปลอดภัยทั้งหมดยังเหมือนเดิมทุกข้อ ได้แก่ `protect` / `removal_candidate` /
`review`, เขตกันชนรอบพืชปลูก, บริเวณที่ไม่มีกรอบไม่ถือเป็นวัชพืช และ
`actuation_authorized: false` ในผลลัพธ์ทุกครั้ง โค้ดใน `src/policy.py` และ
`src/detect.py` ไม่ถูกแก้จากการตัดสินใจครั้งนี้
